🧩 Shared Libraries

Two projects every service depends on: Shared.Common (response envelope, exceptions, middleware, resilience, the idempotency contract, the Redis distributed lock) and Shared.Contracts (every Kafka event schema — the single source of truth so producer and consumer never drift on a payload shape).

1 ApiResponse<T> — one envelope, every service

📄 Common/Models/ApiResponse.cs
public class ApiResponse<T>
{
    public bool Success { get; init; }
    public string Message { get; init; } = string.Empty;
    public T? Data { get; init; }
    public IEnumerable<string> Errors { get; init; } = [];
    public string TraceId { get; init; } = string.Empty;
    public string CorrelationId { get; init; } = string.Empty;

    public static ApiResponse<T> Ok(T data, string message = "") => new() { Success = true, Data = data, Message = message };
    public static ApiResponse<T> Fail(string message, IEnumerable<string>? errors = null) => new() { Success = false, Message = message, Errors = errors ?? [] };
}
// Non-generic ApiResponse : ApiResponse<object> for payload-less responses (logout, revoke-token).

Every controller across all five services returns this shape — a client can always check response.success, read response.data, and correlate a failure back to logs via traceId/correlationId without service-specific parsing.

3 The Redis idempotency pattern — one implementation, atomic check-and-claim

Used to ship as three near-identical Redis-backed classes, one hand-rolled per service (Auth, Inventory, Cart), each doing a separate IsProcessedAsync read followed by a separate MarkProcessedAsync write — a check-then-mark gap that two concurrent callers with the same key could both slip through. Now there's a single RedisIdempotencyService in Shared.Common, parameterized by key prefix so services still don't collide with each other on the shared Redis instance, with the race closed by an atomic claim.

📄 Common/Idempotency/RedisIdempotencyService.cs
public class RedisIdempotencyService(IConnectionMultiplexer redis, string keyPrefix) : IIdempotencyService
{
    public async Task<bool> IsProcessedAsync(string key, CancellationToken ct = default) =>
        await _db.KeyExistsAsync(BuildKey(key));

    public async Task MarkProcessedAsync(string key, TimeSpan? expiry = null, CancellationToken ct = default) =>
        await _db.StringSetAsync(BuildKey(key), "1", expiry ?? DefaultExpiry);

    // The fix: SETNX in one round trip — either this call is the one that claims the key, or it isn't.
    // No window between "check" and "mark" for a second caller to land in.
    public async Task<bool> TryMarkProcessedAsync(string key, TimeSpan? expiry = null, CancellationToken ct = default) =>
        await _db.StringSetAsync(BuildKey(key), "1", expiry ?? DefaultExpiry, When.NotExists);
}

Each service registers it with its own prefix via a factory, e.g. new RedisIdempotencyService(redis, "idempotency:inv:") — same class, three isolated key spaces. TryMarkProcessedAsync is the one callers should reach for; the older two-step methods still exist for call sites that genuinely want a "claim now with a short TTL, extend to a long TTL only after the work actually succeeds" pattern (see Inventory's ReserveAsync).

4 Distributed lock — Redis SETNX, safe release, sorted multi-key acquisition

Idempotency keys answer "has this exact request already been handled?" — a completely different question from "is someone else touching this row right now?" Nothing in the platform answered the second question until IDistributedLockService was added: every Redis usage before this was a one-shot dedup guard, never a lock protecting a read-modify-write against a genuinely concurrent second reader.

📄 Common/Locking/IDistributedLockService.cs
public interface IDistributedLockService
{
    // Retries until `wait` elapses. Returns a handle that releases the lock on DisposeAsync,
    // or null if it couldn't be acquired in time. Auto-expires after `expiry` even if never
    // released, so a crashed holder can never wedge the resource forever.
    Task<IAsyncDisposable?> AcquireAsync(string resource, TimeSpan expiry, TimeSpan wait, CancellationToken ct = default);
}
📄 Common/Locking/RedisDistributedLockService.cs
private const string ReleaseScript = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    else
        return 0
    end
    """;   // only delete if we still hold OUR token — an expired-then-reacquired lock is never stolen back

public async Task<IAsyncDisposable?> AcquireAsync(string resource, TimeSpan expiry, TimeSpan wait, CancellationToken ct = default)
{
    var key = $"lock:{resource}";
    var token = Guid.NewGuid().ToString("N");   // unique per acquisition — this is what the release script checks
    var deadline = DateTime.UtcNow + wait;

    while (true)
    {
        if (await db.StringSetAsync(key, token, expiry, When.NotExists))
            return new LockHandle(db, key, token);
        if (DateTime.UtcNow >= deadline) return null;
        await Task.Delay(RetryInterval, ct);
    }
}

A plain SETNX-with-TTL lock is only safe against one holder at a time if release can't accidentally delete somebody else's lock — the classic bug is holder A's lease expiring, holder B acquiring the same key, then A's delayed Dispose() deleting B's lock. The Lua script closes that: it only deletes when the stored value still matches A's own token.

📄 Common/Locking/DistributedLockExtensions.cs
public static async Task<IAsyncDisposable?> AcquireAllAsync(
    this IDistributedLockService locks, IEnumerable<string> resources, TimeSpan expiry, TimeSpan wait, CancellationToken ct = default)
{
    var ordered = resources.Distinct().OrderBy(r => r, StringComparer.Ordinal).ToList();   // stable order -> no deadlocks
    var acquired = new List<IAsyncDisposable>(ordered.Count);

    foreach (var resource in ordered)
    {
        var handle = await locks.AcquireAsync(resource, expiry, wait, ct);
        if (handle is null) { foreach (var held in acquired) await held.DisposeAsync(); return null; }   // all-or-nothing
        acquired.Add(handle);
    }
    return new CompositeLockHandle(acquired);
}

When a single operation needs to lock several resources at once (e.g. reserving stock across every SKU in a multi-item cart), acquiring them in an arbitrary order is how two concurrent multi-lock operations deadlock each other. Sorting the resource keys first means every caller acquires the same set in the same order, so a cycle can never form.

✅ Where it's actually used
Inventory is the only service wired up to it today — see the Inventory page for how it wraps ReserveAsync/ReleaseAsync/AdjustStockAsync/ReceiveStockAsync and both stock-mutating Kafka consumers. Verified live: 20 truly-concurrent +1 stock-receive calls on one SKU landed on exactly the right final count with zero lost updates and zero 500s; two concurrent over-stock reservations correctly serialized into one success + one clean 422 Insufficient stock instead of a race.

5 Polly resilience policies — retry only, no circuit breaker

📄 Common/Resilience/ResiliencePolicies.cs
public static AsyncRetryPolicy DatabaseRetryPolicy(ILogger logger) =>
    Policy.Handle<Exception>(IsTransient)
        .WaitAndRetryAsync(3, attempt => TimeSpan.FromSeconds(Math.Pow(2, attempt)));   // 2s, 4s, 8s

public static AsyncRetryPolicy KafkaRetryPolicy(ILogger logger) =>
    Policy.Handle<Exception>()
        .WaitAndRetryAsync(5, attempt => TimeSpan.FromSeconds(Math.Pow(2, attempt)));

public static AsyncRetryPolicy HttpRetryPolicy(ILogger logger) =>
    Policy.Handle<HttpRequestException>()
        .WaitAndRetryAsync(3, attempt => TimeSpan.FromMilliseconds(200 * attempt));

Every Kafka producer across the platform (Auth's UserEventProducer, Product's ProductEventProducer, Inventory's InventoryEventProducer, Cart's CartEventProducer) wraps its ProduceAsync call in KafkaRetryPolicy. Underneath that, the Confluent Kafka ProducerConfig itself sets EnableIdempotence = true, Acks = Acks.All, MessageSendMaxRetries = 3 — so there's broker-level idempotence/retry stacked under the application-level Polly retry.

💡 Note
No circuit breaker exists anywhere in the codebase — a downstream outage causes repeated retries rather than a fast-fail/open-circuit response. Fine at current scale; worth revisiting if a dependency's outage duration starts to matter for request latency under load.
