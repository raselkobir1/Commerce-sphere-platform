🛒 Cart Service

The most business-logic-heavy service in the platform. Cart doubles as the order aggregate, orchestrates the checkout saga across Inventory, and is the only service with a full transactional outbox + relay — the textbook pattern for "never lose an event, never send it twice."

1 High-level: the checkout saga end-to-end

There is no distributed transaction spanning Cart and Inventory — there's a saga: a sequence of local transactions, each publishing an event that triggers the next step, with an explicit compensating action if a later step fails.

sequenceDiagram
    participant U as Client
    participant Cart as Cart Service
    participant OB as Outbox table
    participant Relay as OutboxRelay
    participant K as Kafka
    participant Inv as Inventory Service

    U->>Cart: POST /carts/{id}/checkout
    Cart->>Cart: cart.Checkout() (Status=CheckedOut)
    Cart->>OB: insert OutboxMessage(cart-checkedout)
    Note over Cart,OB: cart.Checkout() + outbox row in ONE SaveChangesAsync
    Cart-->>U: 200 OK (cart is CheckedOut)

    loop every 2s
        Relay->>OB: SELECT WHERE ProcessedAt IS NULL
    end
    Relay->>K: produce cart-checkedout
    Relay->>OB: MarkProcessed()

    K->>Inv: cart-checkedout
    Inv->>Inv: reserve stock, sell, confirm reservation

    alt reservation already handled elsewhere
        Inv->>K: inventory-reserved
        K->>Cart: InventorySagaConsumer (logs only — no state change)
    else insufficient stock upstream
        Inv->>K: inventory-reservation-failed
        K->>Cart: InventorySagaConsumer
        Cart->>Cart: RollbackAsync() -> Status=RolledBack
        Cart->>K: CartRolledBackEvent (published directly, NOT via outbox)
    end
⚠️ Read this carefully
The success path (inventory-reserved) does not drive any Cart state change today — it's logged only. The order stays CheckedOut until an admin explicitly calls ConfirmOrderAsync/ShipOrderAsync. Only the failure path (inventory-reservation-failed) triggers real compensation logic.

2 Checkout initiation

📄 src/Services/Cart/CommerceSphere.CartService.Application/Managers/CartManager.cs
public async Task<CartResponse> CheckoutAsync(CheckoutCartRequest request, string correlationId, CancellationToken ct = default)
{
    var cart = await uow.Carts.GetByIdAsync(request.CartId, ct)
        ?? throw new NotFoundException(nameof(Cart), request.CartId);

    if (cart.Status != CartStatus.Active) throw new BusinessException($"Cart {request.CartId} is not Active.");
    if (!cart.Items.Any()) throw new BusinessException("Cannot checkout an empty cart.");

    cart.Checkout();   // marks CheckedOut so it can't be mutated while the saga runs

    var snapshots = cart.Items.Select(i =>
        new CartItemSnapshot(i.ProductId, i.Sku, i.ProductName, i.Quantity, i.UnitPrice)).ToList();

    var checkedOutEvent = new CartCheckedOutEvent(cart.Id, cart.UserId, cart.TotalAmount, snapshots, correlationId, DateTime.UtcNow);
    await uow.Outbox.AddAsync(OutboxMessage.Create(
        CartCheckedOutTopic, cart.Id.ToString(), JsonSerializer.Serialize(checkedOutEvent), "CartCheckedOut", correlationId), ct);

    await uow.SaveChangesAsync(ct);   // cart.Checkout() + outbox insert -> ONE atomic write
    await cacheService.RemoveCartAsync(cart.Id);
    return MapToResponse(cart);
}

Item quantities/prices are snapshotted into the event because the live cart could be mutated or deleted before Inventory ever processes the message — the saga needs a frozen picture of what was actually ordered.

3 Transactional outbox — never lose an event

The dual-write problem: "update the DB" and "publish to Kafka" can't be one atomic operation across two different systems. The outbox pattern turns it into one local DB transaction (state change + an outbox row) plus a separate relay that guarantees at-least-once delivery to Kafka.

📄 src/Services/Cart/CommerceSphere.CartService.Domain/Entities/OutboxMessage.cs
public class OutboxMessage
{
    public string Topic { get; private set; } = string.Empty;
    public string Payload { get; private set; } = string.Empty;   // JSON of the event
    public DateTime? ProcessedAt { get; private set; }            // null = still pending
    public int Attempts { get; private set; }

    public static OutboxMessage Create(string topic, string key, string payload, string eventType, string correlationId) => new() { ... };
    public void MarkProcessed() => ProcessedAt = DateTime.UtcNow;
    public void RecordFailedAttempt() => Attempts++;
}

📄 src/Services/Cart/CommerceSphere.CartService.Infrastructure/Kafka/OutboxRelay.cs
private const int BatchSize = 20;
private static readonly TimeSpan PollInterval = TimeSpan.FromSeconds(2);

protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    var producerConfig = new ProducerConfig
    {
        BootstrapServers = config["Kafka:BootstrapServers"] ?? "localhost:9092",
        EnableIdempotence = true,
        Acks = Acks.All,
    };
    using var producer = new ProducerBuilder<string, string>(producerConfig).Build();

    while (!stoppingToken.IsCancellationRequested)
    {
        try { await PublishPendingAsync(producer, stoppingToken); }
        catch (Exception ex) { logger.LogError(ex, "OutboxRelay loop error."); }
        await Task.Delay(PollInterval, stoppingToken);
    }
}

private async Task PublishPendingAsync(IProducer<string, string> producer, CancellationToken ct)
{
    using var scope = scopeFactory.CreateScope();
    var uow = scope.ServiceProvider.GetRequiredService<IUnitOfWork>();
    var pending = await uow.Outbox.GetUnprocessedAsync(BatchSize, ct);   // WHERE ProcessedAt IS NULL
    if (pending.Count == 0) return;

    foreach (var msg in pending)
    {
        try { await producer.ProduceAsync(msg.Topic, new Message<string,string> { Key = msg.Key, Value = msg.Payload }, ct); msg.MarkProcessed(); }
        catch (Exception) { msg.RecordFailedAttempt(); }   // left unprocessed, retried next poll
    }
    await uow.SaveChangesAsync(ct);   // persists the whole batch's outcome at once
}
💡 At-least-once, not exactly-once
If the process crashes after producer.ProduceAsync succeeds but before SaveChangesAsync marks it processed, the same message gets republished on the next poll. Downstream consumers are expected to dedupe by business key — which is exactly what Inventory's CartCheckedOutConsumer does by checking Reservations.AnyAsync(r => r.CartId == evt.CartId) before acting.

4 The saga consumer — one subscriber, two topics

📄 src/Services/Cart/CommerceSphere.CartService.Infrastructure/Kafka/Consumers/InventorySagaConsumer.cs
consumer.Subscribe([InventoryReservedTopic, InventoryReservationFailedTopic]);
while (!stoppingToken.IsCancellationRequested)
{
    var result = consumer.Consume(stoppingToken);
    if (result is null) continue;
    await ProcessWithRetryAsync(result, stoppingToken);   // 3 attempts, 2s/4s/8s backoff
    consumer.Commit(result);   // offset advances only after processing (or DLQ) completes
}

// Dispatch:
if (result.Topic == InventoryReservationFailedTopic)
{
    var @event = JsonSerializer.Deserialize<InventoryReservationFailedEvent>(result.Message.Value)!;

    // Dedup guard — without this, a redelivered failure event (e.g. crash between processing
    // and committing the Kafka offset) would call RollbackAsync again even if the cart had
    // already moved on to a different terminal state.
    if (!await idempotencyService.TryMarkProcessedAsync($"saga:reservation-failed:{@event.CartId}", TimeSpan.FromDays(7), ct))
        return;   // already handled — skip

    await cartManager.RollbackAsync(@event.CartId, @event.Reason, ct);
}
else // InventoryReservedTopic
{
    var @event = JsonSerializer.Deserialize<InventoryReservedEvent>(result.Message.Value)!;

    if (!await idempotencyService.TryMarkProcessedAsync($"saga:reserved:{@event.CartId}", TimeSpan.FromDays(7), ct))
        return;

    logger.LogInformation("Saga step 2 complete: inventory reserved for CartId={CartId}", @event.CartId);
}

On retry exhaustion the poison message is forwarded to dlq.cart-checkedout with original-topic/error/failed-at headers, and the offset is still committed so one bad message can't stall the whole partition.

✅ Fixed
This was previously the one Kafka consumer in the whole platform with zero dedup guard — redelivery was only implicitly softened by domain-level null/status checks, not an explicit dedupe key. Verified live: publishing the exact same InventoryReservedEvent twice logs "Saga step 2 complete" once, then "Reserved event for cart {CartId} already handled. Skipping." for the redelivery.

5 Compensation — RollbackAsync

📄 CartManager.cs
public async Task RollbackAsync(Guid cartId, string reason, CancellationToken ct = default)
{
    var cart = await uow.Carts.GetByIdAsync(cartId, ct);
    if (cart is null) { logger.LogWarning("Rollback requested for unknown cart {CartId}", cartId); return; }

    cart.Rollback(reason);                     // Status -> RolledBack, appends an OrderStatusEntry
    await uow.SaveChangesAsync(ct);

    await eventProducer.PublishCartRolledBackAsync(new CartRolledBackEvent(
        cart.Id, cart.UserId, reason, string.Empty, DateTime.UtcNow));   // published DIRECTLY — not via outbox

    await cacheService.RemoveCartAsync(cart.Id);
}
🕳️ Asymmetry to flag
Checkout and Cancel write their events through the transactional outbox. RollbackAsync publishes CartRolledBackEvent directly through the Kafka producer instead — this specific event can be silently lost if Kafka happens to be unreachable at that exact instant, unlike checkout/cancel events which are durable in the outbox table until delivered.

6 Idempotency — two mechanisms, both wired up now

(a) DB-based, for cart creation. A Postgres unique partial index backs client-supplied idempotency keys:

if (!string.IsNullOrWhiteSpace(request.IdempotencyKey))
{
    var existing = await uow.Carts.GetByIdempotencyKeyAsync(request.IdempotencyKey, ct);
    if (existing is not null) return MapToResponse(existing);   // replay -> same cart, no duplicate
}
var cart = Cart.Create(request.UserId, request.IdempotencyKey);
builder.HasIndex(c => c.IdempotencyKey).IsUnique()
    .HasDatabaseName("ix_carts_idempotency_key").HasFilter("idempotency_key IS NOT NULL");

(b) Redis IIdempotencyService, in CheckoutAsync. Previously injected into CartManager and never called — checkout was only guarded by the Status != Active check, which two concurrent checkout calls for the same cart could both pass before either saved. Now the checkout claims the cart up front:

📄 CartManager.cs — CheckoutAsync
// Short TTL: enough to cover one request's processing time, not meant to survive into a
// genuinely separate later checkout attempt.
if (!await idempotencyService.TryMarkProcessedAsync($"checkout:{request.CartId}", TimeSpan.FromMinutes(1), ct))
    throw new BusinessException($"Cart {request.CartId} checkout is already being processed.");
✅ Fixed, verified live
Firing two concurrent POST /carts/{cartId}/checkout calls for the same cart now returns one 200 and one clean 422 "checkout is already being processed", instead of racing. InventorySagaConsumer got the same treatment — see §4 above — so both the initiation side and the compensation side of the saga now dedupe explicitly, matching Inventory's ReserveAsync pattern.

7 Domain model — Cart doubles as the order aggregate

There is no separate Order entity. Cart itself carries the full lifecycle via CartStatus: Active → CheckedOut → Confirmed → Shipped, plus Abandoned / RolledBack / Cancelled. "Orders" are just carts filtered by status in the repository layer.

stateDiagram-v2
    [*] --> Active
    Active --> CheckedOut: Checkout()
    CheckedOut --> Confirmed: ConfirmOrderAsync (admin)
    Confirmed --> Shipped: ShipOrderAsync (admin)
    CheckedOut --> RolledBack: RollbackAsync (saga compensation)
    Active --> Abandoned: inactivity
    CheckedOut --> Cancelled: cancel (admin or customer)
    Confirmed --> Cancelled: cancel (admin or customer)
