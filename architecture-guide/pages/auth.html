🔐 Auth Service

Owns every user identity in the platform: JWT + rotating refresh tokens, a real login state machine (lockout → forced password change → 2FA → OTP), RBAC, SSO, and the sole producer of user-created. Also the one place customer-facing cancellation emails get sent from.

1 High-level: identity as the source of truth

Auth is the only service allowed to mint tokens and the only owner of email addresses. Everything else — Cart, Inventory, Notification — trusts the JWT it issues and reacts to the one event it publishes.

2 JWT issuance — access token vs. refresh token

Only the access token is a JWT. The refresh token is a 32-byte CSPRNG opaque string stored in Postgres — never anything a client can decode.

📄 src/Services/Auth/CommerceSphere.AuthService.Infrastructure/Services/JwtService.cs
public string GenerateAccessToken(User user, IEnumerable<string> permissions)
{
    var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_secret));
    var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);
    var claims = new List<Claim> { sub, email, ClaimTypes.Role, firstName, lastName, jti, iat };
    foreach (var permission in permissions)
        claims.Add(new Claim(PermissionClaims.Type, permission));   // RBAC grants baked into the token
    // ... build JwtSecurityToken(issuer, audience, claims, expires: GetAccessTokenExpiry(), creds)
}

Validation side pins the algorithm explicitly (anti alg-confusion attacks) and disables the default 5-minute clock-skew grace:

📄 src/Services/Auth/CommerceSphere.AuthService.API/Program.cs
opts.TokenValidationParameters = new TokenValidationParameters
{
    ValidAlgorithms = new[] { SecurityAlgorithms.HmacSha256 },
    ValidateIssuer = true, ValidateAudience = true, ValidateLifetime = true,
    ClockSkew = TimeSpan.Zero
};

3 Refresh token rotation

📄 src/Services/Auth/CommerceSphere.AuthService.Domain/Entities/RefreshToken.cs
public class RefreshToken : BaseEntity
{
    public string Token { get; private set; }
    public bool IsRevoked { get; private set; }
    public string? ReplacedByToken { get; private set; }   // chain link for rotation
    public bool IsExpired => DateTime.UtcNow >= ExpiresAt;
    public bool IsActive => !IsRevoked && !IsExpired;

    public static RefreshToken Create(Guid userId, string createdByIp, int expiryDays = 7) =>
        new() { Token = Convert.ToBase64String(RandomNumberGenerator.GetBytes(32)), ... };
}
  1. Client calls /refresh-tokenLookup by token value; reject if !IsActive (revoked or expired).
  2. Deactivated-user checkIf the owning user has been deactivated, revoke and reject.
  3. Mint + linkA new RefreshToken is created; the old one calls Revoke(newToken), storing ReplacedByToken as a chain pointer.
  4. Both savedOld token marked revoked, new token active — same DB transaction.
🕳️ Gap worth knowing about
There is no reuse-detection cascade. The standard "stolen refresh token" mitigation walks the ReplacedByToken chain and revokes the entire token family the moment an already-rotated token is replayed. Here, a replayed token is simply rejected (IsActive == false) — the rest of that user's active tokens stay valid. RefreshTokenRepository.RevokeAllForUserAsync exists and is used for admin-triggered password resets, but it isn't wired into this replay path.

4 Login isn't one step — it's a state machine

Order matters: lockout → active check → password → forced password change → 2FA → OTP → tokens. Each intermediate stop returns a ChallengeToken instead of real tokens, and a LoginResult union drives what the controller sends back.

flowchart TD

(5 failed attempts)"}
    B -->|yes| R1["403 — locked 15 min"]
    B -->|no| C{"Account active?"}
    C -->|no| R2["403"]
    C -->|yes| D{"Password valid?
(BCrypt.Verify)"}
    D -->|no| E["RecordFailedLogin()"] --> R3["401"]
    D -->|yes| F{"Must change
temp password?"}
    F -->|yes| R4["ChallengeToken:
LoginNeedsPasswordChange"]
    F -->|no| G{"2FA enabled?"}
    G -->|yes| R5["ChallengeToken:
LoginNeedsTwoFactor"]
    G -->|no| H{"OTP enabled?"}
    H -->|yes| R6["ChallengeToken:
LoginNeedsOtp"]
    H -->|no| I["✅ LoginSucceeded
access + refresh token"]

Lockout state lives directly on the User entity (RecordFailedLogin / IsLockedOut) — 5 failed attempts trigger a 15-minute lockout window, no external service needed. Passwords are hashed with BCrypt (aliased BC), and registration forces role: "Customer" server-side regardless of what the client sends, explicitly closing a privilege-escalation path.

public async Task PublishUserCreatedAsync(UserCreatedEvent evt, CancellationToken ct = default)
{
    var policy = ResiliencePolicies.KafkaRetryPolicy(logger);   // 5 retries, exponential backoff
    await policy.ExecuteAsync(async () =>
    {
        var message = new Message<string, string>
        {
            Key = evt.UserId.ToString(),   // partition key -> per-user ordering
            Value = JsonSerializer.Serialize(evt),
            Headers = new Headers { /* event-type, version, correlation-id */ }
        };

    });
}

Called straight from AuthManager.RegisterAsync after SaveChangesAsync — commit-then-produce, same trade-off as Product's producer (see the Product page).

7 RBAC — Role → Menu → Permission, baked into the JWT

A Menu is not just a sidebar item — it's the securable resource the whole permission system is scoped to. Each menu doubles as a nav entry (Label/Route/Icon, optional ParentId for a tree) and as the unit permissions are granted against.

erDiagram
    ROLE ||--o{ ROLE_MENU_PERMISSION : grants
    MENU ||--o{ ROLE_MENU_PERMISSION : "scoped to"
    ROLE {
      bool IsSystem
      bool IsDefault
    }
    MENU {
      string Key "e.g. products"
      string Label
      string Route
      guid ParentId "nullable, tree"
    }
    ROLE_MENU_PERMISSION {
      bool CanView
      bool CanCreate
      bool CanEdit
      bool CanDelete
    }

One RoleMenuPermission row per (RoleId, MenuId) pair carries a 4-flag CRUD matrix — not one row per action. At login, RolePermissionClaims.Build() flattens every granted flag into a "{menuKey}:{action}" claim string (e.g. "products:create") and bakes the whole set into the JWT under claim type "perm" — the permission set is not re-queried from the database on every request.

📄 src/Shared/CommerceSphere.Shared.Common/Common/Authorization/PermissionAuthorizationHandler.cs
protected override Task HandleRequirementAsync(AuthorizationHandlerContext context, PermissionRequirement requirement)
{
    if (context.User.IsInRole("Admin")) { context.Succeed(requirement); return Task.CompletedTask; }   // Admin bypass — can't lock itself out

    var granted = context.User.Claims.Any(c =>
        c.Type == PermissionClaims.Type &&
        string.Equals(c.Value, requirement.Permission, StringComparison.OrdinalIgnoreCase));
    if (granted) context.Succeed(requirement);
    return Task.CompletedTask;
}

// [HasPermission("products:create")] -> AuthorizeAttribute(policy: "perm:products:create")
// PermissionPolicyProvider builds this policy on the fly for any "perm:" prefixed name —
// no need to pre-register one named policy per permission in the whole platform.

This lives in Shared.Common and is used identically by Auth, Product (ProductController, CategoryController, BannerController, ProductImportController), and Inventory (InventoryController) — a pure JWT-claims check, zero DB round trips per request.

8 SSO, 2FA, OTP, email verification, password reset — one shared primitive underneath

Five features that look separate from the controller list share one mechanism: a Redis-backed ChallengeToken (5-minute TTL) that represents "this login/action is in-progress but not yet complete." Whatever completes the challenge — a TOTP code, an email OTP, a new password — is what actually mints the final JWT/refresh-token pair.

(TOTP code)"]
    CT --> VOTP["POST /otp/verify

    CT --> VPWD["POST /password/complete-forced-change"]

    VPWD --> TOKENS
FeatureMechanism
SSO (Google / Facebook)GET /sso/login/{provider} builds the provider's OAuth URL and stores {provider, redirectUri} + a random CSRF state in Redis (also guards against open redirects via an allow-list). GET /sso/callback resolves the user by (provider, external id) first, then by email — auto-linking a password account to a social login — or creates a new user inside a DB transaction with a unique-constraint fallback for concurrent first-time signups. Issues the same JWT/refresh pair as password login, then redirects the browser to the frontend with tokens in the query string.
2FA (TOTP)RFC 6238 via the OtpNet library. POST /2fa/setup generates a Base32 secret + otpauth:// QR URI; POST /2fa/confirm validates the first code (±1 time-step for clock drift) to activate; POST /2fa/verify completes a pending login challenge.
OTP (email one-time code)Independent of TOTP — a 6-digit code from RandomNumberGenerator (not Random.Shared), stored in Redis with a 5-minute TTL, single-use (deleted on success). Toggled per-user via POST /otp/toggle.
Email verificationToken + expiry stored on the User entity. /verify/resend is deliberately email-enumeration-safe — silently no-ops for an unknown or already-verified address instead of revealing which.
Forgot / reset password/password/forgot always returns success regardless of whether the email exists (same enumeration-safety pattern). /password/reset validates the token, rehashes with BCrypt, and revokes every active refresh token for that user — forces re-login on all devices after a password reset.
Admin-forced password changeA distinct flow from self-service reset: an admin issues a temporary password, and the user is routed through POST /password/complete-forced-change via a ChallengeType.PasswordChange token on their next login — same challenge-token primitive as 2FA/OTP.
Session managementGET /api/auth/sessions lists the caller's own active refresh tokens (IP, created/expiry). DELETE /api/auth/sessions revokes all of them at once. Self-service only — there's no per-session revoke or admin-viewing-another-user's-sessions endpoint.
