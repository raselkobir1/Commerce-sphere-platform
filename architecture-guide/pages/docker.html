🐳 Dockerizing the Whole Application

Every service builds from an identical 4-stage Dockerfile shape. One docker-compose.yml wires up all six services, six Postgres instances, Redis, and Kafka — and two overlay files (override.yml for dev, prod.yml for production) change behaviour without touching the base file.

1 Container topology

One bridge network (commerce-net) holds everything. Each service owns a private Postgres instance — no shared database, matching the per-service-DB microservice rule. Redis and Kafka are the only shared infrastructure.

2 Every service: the same 4-stage Dockerfile

All six microservice Dockerfiles + the API Gateway's follow the identical shape — only the list of copied .csproj references and the final .dll name differ.

📄 src/Services/Auth/CommerceSphere.AuthService.API/Dockerfile
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS base
RUN apt-get update && apt-get install -y curl --no-install-recommends && rm -rf /var/lib/apt/lists/*
WORKDIR /app
EXPOSE 80

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY ["src/Shared/CommerceSphere.Shared.Common/CommerceSphere.Shared.Common.csproj", "src/Shared/CommerceSphere.Shared.Common/"]
COPY ["src/Shared/CommerceSphere.Shared.Contracts/CommerceSphere.Shared.Contracts.csproj", "src/Shared/CommerceSphere.Shared.Contracts/"]
COPY ["src/Services/Auth/CommerceSphere.AuthService.Domain/CommerceSphere.AuthService.Domain.csproj", "src/Services/Auth/CommerceSphere.AuthService.Domain/"]
COPY ["src/Services/Auth/CommerceSphere.AuthService.Application/CommerceSphere.AuthService.Application.csproj", "src/Services/Auth/CommerceSphere.AuthService.Application/"]
COPY ["src/Services/Auth/CommerceSphere.AuthService.Infrastructure/CommerceSphere.AuthService.Infrastructure.csproj", "src/Services/Auth/CommerceSphere.AuthService.Infrastructure/"]
COPY ["src/Services/Auth/CommerceSphere.AuthService.API/CommerceSphere.AuthService.API.csproj", "src/Services/Auth/CommerceSphere.AuthService.API/"]
RUN dotnet restore "src/Services/Auth/CommerceSphere.AuthService.API/CommerceSphere.AuthService.API.csproj"
COPY . .
RUN dotnet build "src/Services/Auth/CommerceSphere.AuthService.API/CommerceSphere.AuthService.API.csproj" -c Release -o /app/build

FROM build AS publish
RUN dotnet publish "src/Services/Auth/CommerceSphere.AuthService.API/CommerceSphere.AuthService.API.csproj" -c Release -o /app/publish /p:UseAppHost=false

FROM base AS final
WORKDIR /app
COPY --from=publish /app/publish .
ENTRYPOINT ["dotnet", "CommerceSphere.AuthService.API.dll"]
  1. baseSlim ASP.NET runtime image + curl installed — specifically so the container healthcheck (curl -f http://localhost:80/health) works without needing the full SDK.
  2. buildFull SDK image. .csproj files are copied and restored before the full source tree — a layer-caching trick: source edits don't invalidate the (slow) restore layer unless a project reference actually changed.
  3. publishdotnet publish -c Release, framework-dependent (UseAppHost=false — no native executable, just the DLL + runtime config).
  4. finalCopies only the published output onto the slim base image — the SDK and full source tree never ship in the final image.

The API Gateway's Dockerfile is the same shape but shorter — it only depends on Shared.Common, not Shared.Contracts or a Domain/Application/Infrastructure stack, since it has no domain logic of its own.

  image: confluentinc/cp-kafka:latest

auth-service:
  build:
    context: .                       # repo root, so the Dockerfile can COPY src/Shared/...
    dockerfile: src/Services/Auth/CommerceSphere.AuthService.API/Dockerfile
  environment:
    ASPNETCORE_ENVIRONMENT: Production
    ConnectionStrings__AuthDb: "Host=postgres-auth;Database=...;Username=commerce;Password=commerce_pass"
  depends_on:
    postgres-auth: { condition: service_healthy }
    redis:         { condition: service_healthy }
    kafka:         { condition: service_healthy }
  restart: unless-stopped
  healthcheck:
    test: ["CMD", "curl", "-f", "http://localhost:80/health"]
    interval: 15s
    timeout: 10s
    retries: 5
    start_period: 20s

cart-service:
  depends_on:
    inventory-service: { condition: service_healthy }   # cross-service saga dependency
    # ...plus its own postgres/redis/kafka

api-gateway:
  ports: ["5000:80"]
  depends_on:
    auth-service: { condition: service_healthy }
    product-service: { condition: service_healthy }
    inventory-service: { condition: service_healthy }
    cart-service: { condition: service_healthy }
    notification-service: { condition: service_healthy }
    chat-service: { condition: service_healthy }

cart-service explicitly waits on inventory-service being healthy before starting — a direct reflection of the checkout saga's dependency (see the Cart page). api-gateway waits on every domain service, since its whole job is to front them.

4 Dev overlay — docker-compose.override.yml (auto-loaded)

Plain docker compose up -d automatically merges this file on top of the base — no -f flags needed. This is what makes local development ergonomic.

  • Sets ASPNETCORE_ENVIRONMENT=Development on every service → Swagger UI at /swagger + detailed error pages + appsettings.Development.json picked up.
  • env_file: .env.development per service, supplying ${JWT_SECRET}, ${GOOGLE_CLIENT_ID}, ${CLOUDINARY_*}, etc., with safe ${VAR:-default} fallbacks.
  • Every port is published to the host — Auth 5211, Product 5095, Inventory 5035, Cart 5236, Notification 5240, Chat 5245, plus every Postgres instance (5433–5438) and redis:6379 — for direct Postman/TablePlus/pgAdmin access.
  • Dev-only tooling added: kafka-ui (browse topics at :8090), pgadmin (:5050), mailpit (SMTP trap — catches verification/OTP/order emails, web UI :8025).
💡 No bind-mount hot reload
The compose file doesn't wire up source-mount hot reload. The documented hybrid workflow instead: run only infra in Docker and each service locally via dotnet run for instant hot reload — 
docker compose up -d postgres-auth postgres-product postgres-inventory postgres-cart redis kafka
dotnet run --project src/Services/Auth/CommerceSphere.AuthService.API

5 Production overlay — docker-compose.prod.yml (explicit -f required)

This file is not auto-loaded — it must be named explicitly, and override.yml is skipped entirely (Compose only auto-merges docker-compose.override.yml, never other override files).

  • Every service gets env_file: .env.production + ASPNETCORE_ENVIRONMENT=Production.
  • Only api-gateway publishes a port (5000:80) — every internal service, every Postgres instance, Redis, and Kafka are unreachable from the host. The inline comment calls this out directly: "only port exposed to the internet."
  • Secrets come from ${VAR} substitution with no dev fallback defaults (unlike the dev overlay's ${VAR:-default}) — a missing production secret fails loudly instead of silently falling back to a dev value.
  • restart: unless-stopped is set at the base-file level and simply inherited here.
  • Comment recommends a CI/CD pipeline inject these as real environment variables rather than writing .env.production to disk on a server.

7 Commands cheat sheet

📄 Build all images
docker compose build
📄 Start the full dev stack (override.yml auto-merged: Swagger on, all ports exposed, kafka-ui/pgadmin/mailpit included)
docker compose up -d
📄 Start production (explicit two -f flags — override.yml is NOT applied)
cp .env.production.example .env.production   # fill in real secrets first, one-time
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
📄 Hybrid dev: infra only in Docker, services run locally via `dotnet run` for hot reload
docker compose up -d postgres-auth postgres-product postgres-inventory postgres-cart redis kafka
dotnet run --project src/Services/Auth/CommerceSphere.AuthService.API
📄 Tear down (keep named volumes / DB data)
docker compose down
📄 Tear down AND wipe all Postgres/Redis data (destructive)
docker compose down -v

No manual EF migration step is needed in any of these flows — every service calls Database.MigrateAsync() automatically on startup (e.g. MigrateAuthDbAsync(), MigrateCartDbAsync()) before it begins serving traffic.
