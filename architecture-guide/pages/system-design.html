🗺️ System Design

Every other page in this guide zooms into one service. This page zooms back out: why the platform is split into these six services and not some other shape, the two topologies that actually connect them (synchronous gateway routing vs. asynchronous Kafka fan-out), one complete customer journey traced hop-by-hop, and a single table of every reliability pattern used anywhere in the codebase — and, just as importantly, where each pattern deliberately isn't used.

1 Synchronous topology — one gateway, six isolated databases

Every client request enters through exactly one door. Every service leaves through exactly one door too — its own Postgres instance. No service holds a connection string to another service's database; the only way data crosses a service boundary is a REST call through the gateway or a Kafka event (next section). That's the whole rule the "microservices" label is enforcing here.

Two things worth noticing that aren't obvious from the per-service pages in isolation: (1) POST /api/inventory/reserve is the only synchronous call one domain service ever makes to another — everything else that crosses a service boundary goes through Kafka. (2) Redis is one shared container, not one-per-service — Auth, Product, Inventory, and Cart all connect to the same instance, each namespacing its own keys with a service-specific prefix (idempotency:*, idempotency:inv:*, idempotency:cart:*, lock:inventory:*) precisely so four services sharing one Redis can't collide on each other's keys.

3 Design rationale — the reasoning, not just the shape

Why these six services, and not some other split? Each boundary lines up with a distinct data lifecycle and load profile, not just a noun in the domain: identity (Auth) changes rarely per user and must be fast on every single request (JWT validation); the catalog (Product) is read-heavy and cacheable; stock (Inventory) is the one place correctness under concurrency matters most (see §4 below); the order lifecycle (Cart) is bursty and is the one flow that must never silently lose a state transition; notifications and chat are both fundamentally fan-out/push problems, but on completely different triggers (Kafka events vs. live REST actions) — which is exactly why they ended up as two services instead of one "communications" service.

Why database-per-service, when a shared database would mean fewer moving parts? A shared database is a shared schema — any service can start joining across another service's tables, and the moment that happens the "service boundary" is fiction; the two services are one system that happens to run in two processes. Six separate Postgres instances make that physically impossible: the only contract between services is Shared.Contracts (the Kafka event schemas) and whatever a REST API explicitly exposes. The cost is real — no cross-service joins, no cross-service transactions — but that cost is what forces every cross-service dependency to be an explicit, versioned contract instead of an implicit one.

Why is POST /inventory/reserve synchronous REST when almost everything else is async Kafka? Because checkout needs a yes/no answer before it writes anything durable — "can this cart even be reserved" gates whether cart.Checkout() happens at all. An event-based "please reserve this" with an eventual "reserved"/"failed" event back would mean either blocking the checkout call on a Kafka round-trip (defeating the point of using Kafka) or optimistically checking out first and unwinding later — which is a strictly worse user experience for the one interaction in the whole platform where the user is actively waiting on the answer.

Why does only Cart have a transactional outbox, when every other service just commits then produces? Blast radius. Losing a product-updated event means a cache or read-model is briefly stale — annoying, self-healing on the next write. Losing a cart-checkedout event means a customer paid and nobody ships the order — a real business incident with no automatic recovery. The outbox pattern (see Cart §3) costs an extra table, a polling relay, and at-least-once (not exactly-once) delivery semantics that every downstream consumer must dedupe against. That cost is worth paying exactly once, for the one event whose loss is unacceptable — not by default everywhere.

Why do idempotency and distributed locking exist as two separate, general-purpose primitives instead of ad-hoc checks per manager? Because both problems are structural, not incidental: Kafka's manual-commit consumers are at-least-once by design — redelivery isn't a bug to fix, it's a guarantee to plan for — and any two concurrent HTTP requests touching the same row will eventually race, regardless of which manager wrote the code. Rather than reinvent a dedupe check or a lock-shaped hack differently in every consumer, Shared.Common ships exactly one IIdempotencyService (atomic Redis SETNX claim) and one IDistributedLockService (Redis SETNX + TTL + token-checked safe release) that any manager can reach for — see §3 and §4 of the Shared Libraries page for the actual code.

4 End-to-end walkthrough — one order, five services, two possible endings

Tracing a single real customer journey end-to-end is the fastest way to see how the synchronous and asynchronous topologies actually interleave. Every hop below carries the same X-Correlation-ID — generated once at the gateway, echoed and logged at every service — so this entire trace is greppable across five separate log files by one value.

  1. Register / log in. Auth issues a JWT carrying role + every menu:action permission claim baked in — no per-request RBAC lookup anywhere downstream.
  2. Create a cart, add items. Pure Cart-local writes — no other service is involved yet.
  3. Reserve stock — the one synchronous cross-service call. Cart → POST /inventory/reserve. Inventory locks every requested SKU (sorted, deadlock-free), atomically claims the idempotency key, then reserves — all-or-nothing across the whole cart. Publishes inventory-reserved/-failed either way.
  4. Checkout. Cart flips to CheckedOut and writes an outbox row in the exact same DB transaction — the 200 response to the client and the guarantee that Kafka will eventually see this event are now decoupled from each other.
  5. Outbox relay publishes, asynchronously. Polls every 2s; if Kafka is briefly unreachable the row simply stays unprocessed and retries next poll — nothing is lost, nothing blocks the client who already got their 200.
  6. Three services react to cart-checkedout independently and in parallel. Inventory sells the stock for real (and can now reject an oversell instead of silently clamping — see Inventory §7); Product decrements the catalog count shown to browsers; Notification pushes an admin alert over SignalR and emails the customer.
  7. Admin confirms, then ships. Two explicit, Kafka-free admin actions — CheckedOut → Confirmed → Shipped. Nothing here is automatic; a human decides.
⚠️ The other ending — insufficient stock discovered at the CONSUMER, not the API
Step 3's synchronous /reserve call can reject up front — but the real checkout path (step 6) is what actually sells stock, and that can also fail (e.g. a race that step 3's lock closes for the API path, but a differently-timed request could still hit at the consumer). When Inventory's Sell() throws, the consumer retries 3× with backoff, then routes the full event to dlq.cart-checkedout for manual reconciliation — stock is left untouched, not driven negative. Separately, if step 3 itself returns inventory-reservation-failed, Cart's saga consumer calls RollbackAsync (idempotency-guarded against redelivery), flips the cart to RolledBack, and publishes cart-rolledback — directly, not via the outbox, the one asymmetric gap named in Cart §5.

6 What's deliberately NOT shared — the isolation boundaries worth remembering

Chat ↔ Kafka
Never connects. REST-persist-then-SignalR-push, fully isolated from the event-driven half of the platform.
Chat ↔ Redis
Never connects either — no SignalR backplane, so real-time delivery only works correctly with exactly one Chat replica.
Notification ↔ Redis
No connection — its idempotency is entirely the Postgres inbox table, not Redis, unlike every other event-driven service.
Any service ↔ another service's Postgres
Never — enforced at the infrastructure level (six separate containers), not just by convention.
Cross-service DB transactions
Don't exist — cannot exist, by construction. Every cross-service consistency guarantee in this platform is a saga (Cart↔Inventory) or eventual consistency (everything else), never a two-phase commit.

None of these are gaps to close — they're boundaries the design leans on. The moment Chat needed multi-replica scale-out, the fix is additive (a Redis backplane), not a redesign; the moment Notification needed Kafka-outage resilience, the inbox pattern already gives it that without Redis at all. The isolation is the point.
