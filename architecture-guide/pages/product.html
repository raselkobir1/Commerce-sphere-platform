2 Cloudinary image pipeline — the actual complex part

Upload is decoupled from Create/Update Product: admins upload an image first, get back a URL, then paste that URL into the product payload. There's no Cloudinary SDK involved — it's a hand-rolled signed multipart upload.

📄 src/Services/Product/CommerceSphere.ProductService.API/Controllers/ImageController.cs
[HttpPost]
[RequestSizeLimit(MaxBytes + 1024)]
public async Task<IActionResult> Upload(IFormFile? file, CancellationToken ct)
{
    if (file is null || file.Length == 0) throw new BusinessException("No image file was provided.");
    if (file.Length > MaxBytes) throw new BusinessException("Image is too large (max 5 MB).");
    if (!AllowedTypes.Contains(file.ContentType)) throw new BusinessException("Unsupported image type...");

    using var buffer = new MemoryStream();
    await file.CopyToAsync(buffer, ct);
    var url = await imageStorage.UploadAsync(buffer.ToArray(), file.FileName, file.ContentType, ct);
    return Ok(ApiResponse<object>.Ok(new { url }, "Image uploaded"));
}

Resize on ingest — Cloudinary itself scales the image down (never up) before storing it, driven by a signed transformation string:

📄 CloudinaryOptions.cs
public int MaxWidth { get; set; } = 1600;
public int MaxHeight { get; set; } = 1600;
public string Quality { get; set; } = "auto:good";
public string Transformation => $"c_limit,w_{MaxWidth},h_{MaxHeight},q_{Quality}";

Delivery optimization (f_auto,q_auto) isn't part of the upload call at all — it's string-spliced into the returned secure_url right after the fact, so every stored ImageUrl already carries automatic format/quality negotiation with zero work from any consumer:

📄 CloudinaryImageStorage.cs
private string ApplyDeliveryTransformation(string secureUrl)
{
    var t = _opts.DeliveryTransformation;   // "f_auto,q_auto"
    const string marker = "/upload/";
    if (string.IsNullOrWhiteSpace(t) || !secureUrl.Contains(marker)) return secureUrl;
    return secureUrl.Replace(marker, $"{marker}{t}/");
}
💡 Note
The upload signature is SHA1 over folder+timestamp+transformation+api_secret. A real gotcha the code works around in a comment: .NET's default Content-Disposition header leaves field names unquoted, which Cloudinary's strict signature parser rejects — the code quotes them explicitly. Registered as a typed HttpClient via IHttpClientFactory (30s timeout) to avoid socket exhaustion, not a bare new HttpClient().

3 Kafka — commit-then-produce, no outbox

📄 src/Services/Product/CommerceSphere.ProductService.Application/Managers/ProductManager.cs
await uow.Products.AddAsync(product, ct);
await uow.SaveChangesAsync(ct);
// Publish AFTER saving so the product ID already exists before Inventory
// tries to create a matching InventoryItem.
var evt = new ProductCreatedEvent(product.Id, product.Name, product.Sku, product.Price,
    product.Stock, correlationId, DateTime.UtcNow);
await eventProducer.PublishProductCreatedAsync(evt, ct);
🕳️ Trade-off to flag
Unlike Cart's transactional outbox (see the Cart page), Product publishes directly to Kafka after the DB commit — no outbox row. If the process crashes between SaveChangesAsync and PublishProductCreatedAsync, Inventory never learns about the new product and no automatic retry recovers it. Mitigated only by a Polly retry policy around the produce call itself, not by durable at-least-once delivery.

Contract: ProductCreatedEvent(ProductId, Name, Sku, Price, InitialStock, CorrelationId, OccurredAt, Version) from Shared.Contracts. A sibling ProductUpdatedEvent fires from UpdateAsync/ActivateAsync/DeactivateAsync. Product also consumes cart-checkedout and cart-cancelled to adjust Stock via DecreaseStock/IncreaseStock.

4 Bulk Excel import — a queued background job, not a request-blocking upload

Admins upload a spreadsheet of hundreds/thousands of products through ProductImportController (api/products/import). This is genuinely non-trivial: the HTTP request only stores the file and enqueues a job — parsing, validation, deduping, insertion and event publishing all happen out-of-band in a background worker.

        W->>DB: COPY BINARY insert valid rows
        W->>K: PublishProductCreatedBatchAsync (fire-and-forget + Flush)
    end
    W->>DB: job.Status = Completed / CompletedWithErrors

    Admin->>Ctrl: GET /import/{jobId}/errors
    Ctrl-->>Admin: errors.xlsx (Row/Sku/Reason)

Template + parsing — ClosedXML

Both the template generator and the parser use ClosedXML (`XLWorkbook`, DOM-based). The template ships a Products sheet (columns Name, Description, Sku, Price, Category, ImageUrl, InitialStock, required subset in bold) plus an Instructions sheet explaining that duplicate/existing SKUs get skipped and reported. A code comment explicitly flags the memory trade-off — loading a full workbook costs ~150-300MB for 100K rows, judged acceptable "for an infrequent admin background job," with a SAX-based DocumentFormat.OpenXml reader suggested if files get an order of magnitude bigger.

    // Pending(0) -> Processing(1) -> Completed(2) / CompletedWithErrors(3) / Failed(4)
}

The upload endpoint saves the raw file before creating the job row, so a worker can never dequeue a job whose file is missing. Enqueue is an in-memory, single-reader System.Threading.Channels.Channel<Guid> (BulkImportQueue) — fast, but a process restart loses any queued-but-undequeued job id; the DB row is left Pending with no startup requeue implemented yet.

Per-row validation + error report

📄 ProductImportService.cs
var validation = rowValidator.Validate(row);
if (!validation.IsValid)
{
    errors.Add(new ProductImportError(
        row.RowNumber, row.Sku, string.Join("; ", validation.Errors.Select(e => e.ErrorMessage))));
    continue;
}
// duplicate SKU within the SAME file:
if (!seenInFile.Add(row.Sku.Trim().ToUpperInvariant()))
{
    errors.Add(new ProductImportError(row.RowNumber, row.Sku, "Duplicate SKU within the uploaded file."));
    continue;
}
// SKU already exists in the catalog (checked via one ANY(@skus) query before the batch insert):
if (existingSkus.Contains(row.Sku)) { errors.Add(new ProductImportError(row.RowNumber, row.Sku, "A product with this SKU already exists.")); continue; }

GET /{jobId}/errors doesn't return JSON — it streams back an .xlsx report (columns Row / Sku / Reason) built the same way as the template, only persisted if at least one row failed. Rows with a cell-conversion failure (ParseError, e.g. non-numeric Price) skip field-level validation entirely and go straight to the error list.

Bulk insert — PostgreSQL binary COPY, not EF SaveChanges

Rows are chunked into batches of 5,000. Valid rows in a batch bypass EF's change tracker completely and go through NpgsqlBinaryImporter:

📄 NpgsqlProductBulkInserter.cs
private const string CopyCommand =
    "COPY products (id, name, description, sku, price, category, image_url, " +
    "is_active, is_published, stock, created_at, updated_at) FROM STDIN (FORMAT BINARY)";

await using var writer = await connection.BeginBinaryImportAsync(CopyCommand, ct);
foreach (var p in products) { await writer.StartRowAsync(ct); await writer.WriteAsync(...); }
await writer.CompleteAsync(ct);

Imported products land as drafts (IsPublished = false), same as single-product creation.

Kafka — batched fire-and-forget, not the awaited single-event path

📄 ProductEventProducer.cs
public Task PublishProductCreatedBatchAsync(IEnumerable<ProductCreatedEvent> events, CancellationToken ct = default)
{
    foreach (var evt in events)
    {
        var message = new Message<string, string> { Key = evt.ProductId.ToString(), Value = JsonSerializer.Serialize(evt) };
        // Non-blocking enqueue: the delivery handler only logs failures, never retries.
        _producer.Produce("product-created", message, report =>
        {
            if (report.Error.IsError) logger.LogError("Failed to deliver batched event. ProductId: {ProductId}", evt.ProductId);
        });
    }
    _producer.Flush(ct);   // block once, at the end, until every queued message is delivered/errored
    return Task.CompletedTask;
}

This trades per-message retry/backpressure (which the single-product PublishProductCreatedAsync path has, via a Polly retry policy around an awaited ProduceAsync) for throughput: no N-times network-round-trip awaits for N products — librdkafka's internal queue absorbs the burst, and one Flush synchronizes at the end.

🕳️ Same dual-write trade-off as single-create, at bigger scale
The insert (COPY) and the batch Kafka publish are still two separate steps with no outbox tying them together — a crash between them leaves Inventory missing however many SKUs were in that batch. The ProductCreatedConsumer being idempotent (see the Inventory page) means the recovery path is a manual re-publish, not automatic replay.

5 Redis — read-through cache, best-effort

📄 src/Services/Product/CommerceSphere.ProductService.Infrastructure/Redis/ProductCacheService.cs
try
{
    var value = await _db.StringGetAsync(CacheKey(id));
    if (value.IsNullOrEmpty) return null;
    return JsonSerializer.Deserialize<ProductResponse>(value!);
}
catch (Exception ex)
{
    logger.LogWarning(ex, "Redis GET failed for ProductId: {ProductId}. Falling back to database.", id);
    return null;   // Redis is a best-effort accelerator, never a hard dependency
}

Key pattern product:{guid}, 5-minute TTL. Every mutation (Create/Update/Activate/Deactivate) invalidates then write-through re-populates the cache.

6 Categories & banners — the two storefront-taxonomy siblings, easy to overlook

Two more controllers hang off this service that never come up when people describe "the product API": CategoryController and BannerController. Same permission-gated CRUD shape as everything else, worth naming so they don't get mistaken for missing endpoints.

ShapeNotes
Categoryapi/categories — full CRUD, hierarchical via nullable ParentId (added by the AddCategoryParent migration)A real separate entity/table with its own admin management screen — but Product.Category itself is still just a trimmed string field (see the business rules below), not a foreign key into this table. The two aren't yet linked at the data level.
Bannerapi/banners — full CRUD for storefront carousel bannersGated by [HasPermission("banners:create/edit/delete")]; the banners menu was one of the entries backfilled by SeedRbacAsync onto existing installs (see the Auth RBAC section) rather than present since day one.

Public reads (GET) are anonymous for both — the storefront needs the category list and active banners without a login; create/update/delete require the matching [HasPermission] claim, same RBAC model used everywhere else in the platform.

7 Business rules worth knowing

  • SKU normalization — Trim().ToUpperInvariant() in both the manager and the domain factory, so "abc-001" and "ABC-001" collide on the uniqueness check → ConflictException (409).
  • Draft-first publishing — new products are IsActive=true but IsPublished=false; only storefront-visible after an explicit admin Publish(), supporting bulk publish/unpublish by ID list.
  • Stock is never touched via REST — DecreaseStock/IncreaseStock are driven purely by the Kafka consumers reacting to checkout/cancellation, clamped at zero.
  • Belt-and-suspenders validation — price/stock non-negativity is checked both in FluentValidation and again inside the domain factory (ArgumentException).
