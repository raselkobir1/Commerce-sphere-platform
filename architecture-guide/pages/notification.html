🔔 Notification Service

A pure consumer with no upstream producer of its own. This is where the platform's reliability patterns are most concentrated: manual-commit consumption, inbox-table idempotency, a dead-letter queue, live SignalR push, and transactional customer email.

2 Manual-commit consumer — resume-from-offset after downtime

📄 src/Services/Notification/CommerceSphere.NotificationService.Infrastructure/Kafka/Consumers/NotificationConsumer.cs
var consumerConfig = new ConsumerConfig
{
    BootstrapServers = bootstrap,
    GroupId = ConsumerGroup,
    AutoOffsetReset = AutoOffsetReset.Earliest,
    EnableAutoCommit = false
};
consumer.Subscribe([CheckedOutTopic, CancelledTopic, UserCreatedTopic]);

while (!stoppingToken.IsCancellationRequested)
{
    var result = consumer.Consume(stoppingToken);
    if (result?.Message?.Value is null) continue;
    await ProcessWithRetryAsync(result, dlqProducer, stoppingToken);
    consumer.Commit(result);   // commit only after processing succeeds (or is dead-lettered)
}

Because the commit call sits after processing, a crash mid-handling means the offset never advances — on restart the consumer resumes from the last committed offset and re-delivers that message. Nothing is skipped across downtime. AutoOffsetReset.Earliest also means a brand-new consumer group replays full topic history, which is exactly how the UserContact read-model backfills itself on first deploy.

3 Inbox idempotency — exactly-once notifications despite at-least-once delivery

📄 src/Services/Notification/CommerceSphere.NotificationService.Domain/Entities/InboxMessage.cs
public class InboxMessage
{
    public string Key { get; private set; } = string.Empty;   // IS the primary key, not a Guid
    public DateTime ProcessedAt { get; private set; } = DateTime.UtcNow;
    public static InboxMessage For(string key) => new() { Key = key };
}
📄 .../Application/Handlers/OrderEventHandler.cs
var key = $"checkedout:{evt.CartId}";
if (await uow.Inbox.ExistsAsync(key, ct))
{
    logger.LogInformation("Order {OrderId} already notified. Skipping.", evt.CartId);
    return;                       // redelivered message -> no-op, no double email/notification
}
// ... side effects (email, SignalR push) run BEFORE the inbox row commits ...
await uow.Notifications.AddAsync(notification, ct);
await uow.Inbox.AddAsync(InboxMessage.For(key), ct);
await uow.SaveChangesAsync(ct);   // notification row + inbox row committed atomically together

Design intent: side effects run before the inbox row is committed, so a transient failure (e.g. SMTP timeout) gets naturally retried by Kafka redelivery rather than silently dropped — while the notification + inbox row commit atomically in one SaveChangesAsync, giving an exactly-once in-app record even across a crash. Cancellation uses key cancelled:{cartId}; user-created skips the inbox entirely since its handler is a natural upsert (idempotent by construction). The Key column is itself the table's primary key, so even a race past the ExistsAsync check fails at the DB constraint level as a backstop.

4 Dead-letter queue — 3 retries, exponential backoff, one shared DLQ

📄 NotificationConsumer.cs
private async Task ProcessWithRetryAsync(ConsumeResult<string, string> result, IProducer<string, string> dlq, CancellationToken ct)
{
    var attempt = 0;
    while (attempt < MaxRetries)   // MaxRetries = 3
    {
        try { await DispatchAsync(result.Topic, result.Message.Value, ct); return; }
        catch (Exception ex)
        {
            attempt++;
            if (attempt >= MaxRetries)
            {
                var msg = new Message<string, string>
                {
                    Key = result.Message.Key, Value = result.Message.Value,
                    Headers = [new Header("source-topic", Encoding.UTF8.GetBytes(result.Topic))]
                };
                await dlq.ProduceAsync("dlq.notifications", msg, ct);   // poison message, one shared DLQ topic
                return;
            }
            await Task.Delay(TimeSpan.FromSeconds(Math.Pow(2, attempt)), ct);   // 2s, then 4s
        }
    }
}

Unlike Cart/Inventory which each have their own per-source DLQ topic, Notification funnels every failure into a single dlq.notifications topic, tagged with a source-topic header so the origin can still be recovered for replay. After either success or dead-lettering, the outer loop still calls consumer.Commit(result) — a poison message's offset is committed, so it can't block the partition forever, at the cost of that one message needing manual recovery from the DLQ.

5 Two notification channels

(a) Admin in-app — SignalR push + REST feed

📄 src/Services/Notification/CommerceSphere.NotificationService.API/Realtime/NotificationHub.cs
[Authorize(Roles = "Admin")]
public class NotificationHub : Hub { }   // pure server -> client push, no client-callable methods

public class SignalRRealtimeNotifier(IHubContext<NotificationHub> hub) : IRealtimeNotifier
{
    public Task NotificationCreatedAsync(NotificationResponse n, CancellationToken ct = default) =>
        hub.Clients.All.SendAsync("notification", n, ct);
}

Since browsers can't set an Authorization header on a WebSocket handshake, the JWT is pulled from the query string specifically for hub paths:

opts.Events = new JwtBearerEvents
{
    OnMessageReceived = context =>
    {
        var accessToken = context.Request.Query["access_token"];
        if (!string.IsNullOrEmpty(accessToken) && context.HttpContext.Request.Path.StartsWithSegments("/hubs"))
            context.Token = accessToken;
        return Task.CompletedTask;
    }
};

REST feed for initial load / polling fallback: GET /api/notifications (recent 30 + unread count), POST /api/notifications/read, POST /api/notifications/read-all — all [Authorize(Roles = "Admin")].

6 Operational follow-up

🕳️ Unbounded inbox growth
No background job prunes old inbox_messages rows — the table grows forever since every processed event leaves a permanent dedupe marker. A TTL/retention job (delete rows older than N days, since Kafka retention itself bounds how far back a redelivery could ever come from) would be a reasonable addition.
