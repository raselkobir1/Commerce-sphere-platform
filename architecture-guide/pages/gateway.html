🚪 API Gateway

The single front door for every client. Routes by path prefix to internal Docker DNS names, terminates JWT auth, rate-limits, injects a correlation ID that threads through every downstream log line, and actively health-checks every cluster.

1 High-level: one door, six services behind it

Every external call — from the storefront, the admin panel, or Postman — hits the gateway on :5000. Nothing talks to auth-service, product-service, etc. directly; the gateway is the only container with a published port in production.

All internal hops use Docker's bridge network (commerce-net) and Docker DNS — http://auth-service:80 resolves without any service discovery infra.

2 Low-level: routes → clusters → destinations

YARP config lives entirely in appsettings.json — no C# route-building code. A route matches a path pattern and points at a cluster; a cluster holds one or more physical destinations plus its own load-balancing and health-check policy.

📄 src/ApiGateway/CommerceSphere.ApiGateway/appsettings.json
"Routes": {
  "auth-route":      { "ClusterId": "auth-cluster",      "Match": { "Path": "/api/auth/{**catch-all}" } },
  "products-route":  { "ClusterId": "product-cluster",   "Match": { "Path": "/api/products/{**catch-all}" } },
  "inventory-route": { "ClusterId": "inventory-cluster", "AuthorizationPolicy": "default",
                        "Match": { "Path": "/api/inventory/{**catch-all}" } },
  "cart-route":      { "ClusterId": "cart-cluster",      "AuthorizationPolicy": "default",
                        "Match": { "Path": "/api/carts/{**catch-all}" } },
  "chat-hub-route":  { "ClusterId": "chat-cluster",      "Match": { "Path": "/hubs/chat/{**catch-all}" } }
},
"Clusters": {
  "auth-cluster": {
    "LoadBalancingPolicy": "RoundRobin",
    "HealthCheck": {
      "Active": { "Enabled": true, "Interval": "00:00:10", "Timeout": "00:00:10",
                  "Policy": "ConsecutiveFailures", "Path": "/health" }
    },
    "Destinations": { "auth-service/primary": { "Address": "http://auth-service:80" } }
  }
}

💡 Note
Each service still enforces its own [Authorize]/[HasPermission] attributes independently — the gateway's AuthorizationPolicy is a coarse first gate, not the only one. Defense in depth: a request that somehow bypasses the gateway still can't reach a protected controller action without a valid JWT.

3 JWT validation at the edge

The gateway validates the same HS256 JWT that Auth issues, using the shared Jwt:Secret. Rejected tokens never reach a downstream service.

📄 src/ApiGateway/CommerceSphere.ApiGateway/Program.cs
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(opts =>
    {
        opts.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            ValidIssuer = jwtSection["Issuer"],
            ValidAudience = jwtSection["Audience"],
            IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(jwtSection["Secret"]!)),
            ClockSkew = TimeSpan.Zero   // deliberate: no 5-minute default grace period
        };
    });

After validation succeeds, a YARP transform pipeline re-derives trusted headers from the token's claims and forwards them downstream, so services never need to re-parse the JWT themselves for basic identity:

4 Rate limiting — 200 req/min, fixed window

📄 src/ApiGateway/CommerceSphere.ApiGateway/Program.cs
builder.Services.AddRateLimiter(opts =>
{
    opts.AddFixedWindowLimiter("gateway-fixed", o =>
    {
        o.Window = TimeSpan.FromMinutes(1);
        o.PermitLimit = 200;
        o.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
        o.QueueLimit = 20;
    });
    opts.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});

Applied per route via "RateLimiterPolicy": "gateway-fixed". A burst beyond 200/min queues up to 20 requests (oldest served first) before returning 429 — smoother than a hard cutoff, but still bounded.

5 Correlation ID propagation

Every request gets (or keeps) an X-Correlation-ID header at the gateway, which every downstream service's GlobalExceptionMiddleware and log scope reads back — one ID to grep across five services' log files for a single user action.

sequenceDiagram
    participant C as Client
    participant G as Gateway
    participant S as Any downstream service
    C->>G: Request (no X-Correlation-ID)
    G->>G: generate new correlation id
    G->>S: forward + X-Correlation-ID
    S->>S: attach id to log scope + ApiResponse.CorrelationId
    S-->>G: response
    G-->>C: response + X-Correlation-ID echoed

6 Active health checks

Each cluster can define an Active health check that YARP polls independently of live traffic — a service that starts failing /health is pulled out of rotation before real requests hit it.

⚠️ Coverage gap
Only auth-cluster and product-cluster currently have the HealthCheck.Active block wired in appsettings.json. Inventory, Cart, Notification and Chat clusters route traffic without an active health probe at the gateway layer — worth adding for parity, since Docker Compose's own service_healthy gate only protects startup ordering, not runtime routing decisions.
