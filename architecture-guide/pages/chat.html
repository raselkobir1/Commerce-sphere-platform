💬 Chat Service

Easy to miss entirely — it never appears in the Kafka topic table because it doesn't touch Kafka at all. One-to-one live support chat between a customer and any Admin-role agent, persisted via REST first and pushed live over SignalR second. Fully wired into the gateway and docker-compose, not aspirational config.

src/Services/Chat Postgres :chat-db /hubs/chat No Kafka involved Single-instance SignalR (no backplane)
High-level Persist-then-push SignalR hub & groups Domain model & routes Scaling caveat

1 High-level: not event-driven — request/response + a live push on top

Every other service in this guide talks Kafka. Chat doesn't need to — a chat message only matters to two participants in real time, not to the rest of the platform, so there's no event bus involved at all. It's the simplest service in the repo mechanically, and the easiest one to miss when cataloguing "what talks to what."

Each customer has exactly one persistent conversation thread with support — Conversation.Start creates it lazily on first contact, there's no "start a new ticket" concept. Agents see every open conversation in a shared inbox (`support` group), not a per-agent queue.

2 Persist-then-push — REST is the source of truth, SignalR is just delivery

This is the opposite order from Notification's Kafka flow: here, the write happens synchronously in the HTTP request before anything gets pushed. If the SignalR push fails (client offline, hub blip), the message is still safely in Postgres — the next REST fetch of message history picks it up.

📄 src/Services/Chat/CommerceSphere.ChatService.Application/Managers/ChatManager.cs (shape)
public async Task<ChatMessageResponse> SendMessageAsync(Guid conversationId, SendMessageRequest request, ChatUser sender, CancellationToken ct)
{
    var conversation = await uow.Conversations.GetByIdAsync(conversationId, ct)
        ?? throw new NotFoundException(nameof(Conversation), conversationId);

    var message = ChatMessage.Create(conversationId, sender.Id, sender.Role, sender.Name, request.Content);
    await uow.Messages.AddAsync(message, ct);

    conversation.RecordActivity(message.Content, message.CreatedAt, unreadForSupport: sender.Role == "Customer");
    await uow.SaveChangesAsync(ct);   // durable write FIRST

    var response = MapToResponse(message);
    await notifier.MessageSentAsync(conversationId, response, ct);   // then push live — best-effort
    return response;
}

Conversation denormalizes LastMessageAt/LastMessagePreview/UnreadForSupport directly on the row specifically so the agent inbox list (GET /api/chat/conversations, sorted by recency) is a single flat query — no join against a million-row message table just to render a preview list.

3 SignalR hub — two group scopes, JWT over the WebSocket handshake

📄 src/Services/Chat/CommerceSphere.ChatService.API/Realtime/ChatHub.cs
public class ChatHub : Hub
{
    public async Task JoinConversation(Guid conversationId) =>
        await Groups.AddToGroupAsync(Context.ConnectionId, $"conv:{conversationId}");

    public async Task LeaveConversation(Guid conversationId) =>
        await Groups.RemoveFromGroupAsync(Context.ConnectionId, $"conv:{conversationId}");

    public async Task Typing(Guid conversationId) =>
        await Clients.OthersInGroup($"conv:{conversationId}").SendAsync("typing", Context.User?.Identity?.Name);

    public override async Task OnConnectedAsync()
    {
        if (Context.User?.IsInRole("Admin") == true)
            await Groups.AddToGroupAsync(Context.ConnectionId, "support");   // agents auto-join the shared inbox group
        await base.OnConnectedAsync();
    }
}
GroupMembersPurpose
conv:{conversationId}the customer + any agent(s) viewing that threadmessage delivery, typing indicator
supportevery connected Admin-role agentlive inbox updates (new/updated conversation) without opening a thread

Same JWT-over-WebSocket trick as Notification's hub — browsers can't set an Authorization header on a WS handshake, so the token travels as ?access_token= and gets pulled into context.Token via JwtBearerEvents.OnMessageReceived, scoped to /hubs paths in Program.cs.

💡 RBAC tie-in
Auth's RBAC seed (SeedRbacAsync) provisions a dedicated support-chat admin menu entry — direct evidence this is a first-class, intentionally integrated feature and not leftover scaffolding. See the Auth page's RBAC section.

5 Scaling caveat

🕳️ No SignalR backplane configured
The hub runs with SignalR's default in-memory connection tracking — fine for a single chat-service replica, but if it's ever scaled to 2+ instances behind the gateway's round-robin load balancer, a customer connected to instance A and an agent connected to instance B would never receive each other's live pushes (Groups are per-instance in memory). Adding a Redis backplane (AddStackExchangeRedis(...) on the SignalR builder — the same Redis container already shared by every other service) would fix this before horizontally scaling Chat.
