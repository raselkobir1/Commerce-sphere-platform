Domain service · Stock & reservations

📦 Inventory Service

A hybrid: a synchronous REST reservation API guarded by Redis idempotency keys and a Redis distributed lock around every stock mutation, plus three background Kafka consumers keeping stock in sync with the catalog and the checkout saga — and the service that fires the saga's success/failure signal back to Cart.

1 High-level: not a "reserve" topic — a synchronous API

A common misconception: Cart doesn't publish a "reserve stock" event that Inventory consumes. Cart calls POST /api/inventory/reserve synchronously, and Inventory then publishes the outcome for Cart's saga consumer to react to asynchronously. Kafka drives the compensation/sync side, not the initial ask.

2 Reservation logic — all-or-nothing per SKU

📄 src/Services/Inventory/CommerceSphere.InventoryService.Domain/Entities/InventoryItem.cs
public void Reserve(int qty)
{
    if (qty <= 0) throw new BusinessException("Reserve quantity must be greater than zero.");
    if (QuantityAvailable < qty)
        throw new BusinessException(
            $"Insufficient stock for SKU '{Sku}'. Available: {QuantityAvailable}, Requested: {qty}.");
    QuantityReserved += qty;
    SetUpdated();
}
// QuantityAvailable => QuantityOnHand - QuantityReserved (computed — reserved tracked separately from on-hand)

InventoryManager.ReserveAsync opens a DB transaction, loops every requested SKU calling Reserve(qty). If any line fails — SKU not found or insufficient stock — the whole transaction rolls back: no partial reservations across a multi-item cart. On success it commits, publishes InventoryReservedEvent, and marks the idempotency key processed; on failure it rolls back and publishes InventoryReservationFailedEvent instead.

Before touching the DB at all, it now acquires a Redis lock over every SKU in the request (sorted, via AcquireAllAsync) — see §7 for why that matters. The DB transaction itself changed shape too:

📄 UnitOfWork/UnitOfWork.cs
// db.Database.BeginTransactionAsync() directly is INCOMPATIBLE with EnableRetryOnFailure —
// any query run inside that manual transaction throws InvalidOperationException. This wasn't
// hit before because nothing in the live checkout path ever called ReserveAsync/ReleaseAsync.
public async Task<T> ExecuteInTransactionAsync<T>(Func<Task<T>> operation, CancellationToken ct = default)
{
    var strategy = db.Database.CreateExecutionStrategy();
    return await strategy.ExecuteAsync(async () =>
    {
        await using var transaction = await db.Database.BeginTransactionAsync(ct);
        try { var result = await operation(); await transaction.CommitAsync(ct); return result; }
        catch { await transaction.RollbackAsync(ct); throw; }
    });
}
🕳️ Found while verifying the lock fix, not related to it
Every call to ReserveAsync/ReleaseAsync threw a 500 before this — a pre-existing EF Core / Npgsql incompatibility that had simply never been exercised, since the real checkout path bypasses these methods entirely (see the high-level diagram above: Cart calls POST /reserve synchronously, but nothing in the live cart-checkedout flow does).

3 Kafka consumers — DB-state idempotency, not Redis

📄 .../Kafka/Consumers/CartCheckedOutConsumer.cs
if (await db.Reservations.AnyAsync(r => r.CartId == evt.CartId, ct))
{
    logger.LogInformation("Checkout {CartId} already applied. Skipping.", evt.CartId);
    return;
}

// Lock every SKU being sold (sorted, via AcquireAllAsync) before reading ANY of them —
// no other consumer instance can touch these rows until this checkout is fully saved.
var lockKeys = evt.Items.Select(i => $"inventory:{i.ProductId}");
await using var stockLock = await lockService.AcquireAllAsync(lockKeys, LockExpiry, LockWait, ct)
    ?? throw new InvalidOperationException($"Could not acquire inventory lock for checkout {evt.CartId}.");

foreach (var item in evt.Items)
{
    var inv = await db.InventoryItems.FirstOrDefaultAsync(i => i.ProductId == item.ProductId, ct);
    inv?.Sell(item.Quantity);   // throws BusinessException on insufficient stock — see below
}
var reservation = Reservation.Create(evt.CartId, evt.UserId, evt.CartId.ToString(), items);
reservation.Confirm();
await db.Reservations.AddAsync(reservation, ct);
await db.SaveChangesAsync(ct);
📄 Domain/Entities/InventoryItem.cs
// Was: QuantityOnHand = Math.Max(0, QuantityOnHand - qty);  — clamped to zero, so an oversell
// couldn't even be DETECTED, let alone prevented. Now:
public void Sell(int qty)
{
    if (qty <= 0) throw new BusinessException("Sell quantity must be greater than zero.");
    if (QuantityOnHand < qty)
        throw new BusinessException($"Insufficient stock for SKU '{Sku}'. On hand: {QuantityOnHand}, Requested: {qty}.");
    QuantityOnHand -= qty;
    QuantityReserved = Math.Max(0, QuantityReserved - qty);
    SetUpdated();
}
✅ Verified live
Checked out a cart for 5 units against 1 in stock: Sell() threw, the consumer retried 3× with backoff, then routed the full event payload to dlq.cart-checkedout — and stock stayed at 1. Before this fix the same scenario silently clamped to 0 and fabricated a "confirmed" reservation with no trace anywhere.

All three consumers (ProductCreatedConsumer, CartCheckedOutConsumer, CartCancelledConsumer) are BackgroundServices with manual commit, exponential-backoff retry, and DLQ on exhaustion — same shape as every other consumer in the platform. CartCancelledConsumer's restock loop takes the same per-SKU lock before calling ReceiveStock.

5 Compensation — two independent rollback paths

📄 src/Services/Inventory/CommerceSphere.InventoryService.Domain/Entities/InventoryItem.cs
public void Release(int qty)
{
    if (qty <= 0) throw new BusinessException("Release quantity must be greater than zero.");
    // Math.Max guards against a reserved count going negative if a release is replayed
    QuantityReserved = Math.Max(0, QuantityReserved - qty);
    SetUpdated();
}

(a) Explicit release — InventoryManager.ReleaseAsync, application-triggered, publishes InventoryReleasedEvent. (b) Event-driven restock on cancellation — CartCancelledConsumer restocks quantities already sold, guarded against replay by checking Reservation.Status == Confirmed before acting:

if (reservation.Status != ReservationStatus.Confirmed)
{
    logger.LogInformation("Cancel for {CartId} already restocked. Skipping.", evt.CartId);
    return;
}
foreach (var item in evt.Items) { var inv = ...; inv?.ReceiveStock(item.Quantity); }
reservation.Cancel();

6 Redis idempotency — atomic claim, not check-then-mark

📄 Application/Managers/InventoryManager.cs — ReserveAsync
// Atomically claim the key with a SHORT TTL up front. If the reservation goes on to fail
// (insufficient stock, SKU not found), the claim just expires — a legitimate retry isn't
// blocked. Only on success is it re-marked with a long TTL.
if (!await idempotencyService.TryMarkProcessedAsync(request.IdempotencyKey, TimeSpan.FromMinutes(1), ct))
    throw new IdempotencyException(request.IdempotencyKey);
// ... reservation succeeds ...
await idempotencyService.MarkProcessedAsync(request.IdempotencyKey, TimeSpan.FromHours(24), ct);

Used in ReserveAsync, guarding client retries of the same HTTP call via the X-Idempotency-Key header — a replay throws IdempotencyException (409), verified live: firing the same key twice returns 200 then a clean 409. See Shared Libraries for why this claim-then-extend shape replaced a plain IsProcessedAsync/MarkProcessedAsync pair. The three Kafka consumers still deliberately use DB-state checks instead (row existence, Reservation.Status) rather than Redis — HTTP-facing idempotency uses Redis, event-driven idempotency uses the database as the source of truth.

7 Distributed lock — closing the concurrent-reservation race

Idempotency alone doesn't stop two different requests from racing on the same SKU — two different carts, two different idempotency keys, both reserving the last unit of the same product. Every stock mutation in this service (ReserveAsync, ReleaseAsync, AdjustStockAsync, ReceiveStockAsync, and both Kafka consumers) now wraps its read-modify-write in a Redis lock keyed by inventory:{productId}.

📄 Application/Managers/InventoryManager.cs
private static string StockLockKey(Guid productId) => $"inventory:{productId}";

// Single SKU (AdjustStockAsync / ReceiveStockAsync):
await using var stockLock = await lockService.AcquireAsync(StockLockKey(request.ProductId), LockExpiry, LockWait, ct)
    ?? throw new BusinessException("Inventory is busy processing another update for this item. Please retry.");

// Multiple SKUs in one call (ReserveAsync / ReleaseAsync) — sorted, deadlock-free:
var lockKeys = request.Items.Select(i => StockLockKey(i.ProductId));
await using var stockLock = await lockService.AcquireAllAsync(lockKeys, LockExpiry, LockWait, ct)
    ?? throw new BusinessException("Inventory is busy processing another update for one of these items. Please retry.");
✅ Verified live, two ways
Pure concurrency: 20 truly-concurrent POST /inventory/receive calls (+1 each) on one SKU → all 200, final stock exactly right, zero lost updates.
Race + business rule together: two concurrent POST /inventory/reserve calls for 20 units each against 30 available → first succeeded; the second waited for the lock, then read the already-updated stock fresh and correctly got 422 Insufficient stock. Available: 10, Requested: 20 — not a stale read, not a raw DB exception, not a silent oversell.

8 Manual stock corrections — Adjust vs. Receive, easy to conflate

Beyond the saga's reserve/release/sell/restock flow, admins have two direct write paths onto InventoryItem that never touch Kafka at all — worth naming since they're semantically different operations, not two names for the same thing.

EndpointMethodSemantics
POST /api/inventory/adjustInventoryManager.AdjustStockAsyncSets QuantityOnHand to an absolute new value — a correction/audit action (e.g. after a physical stocktake finds a discrepancy).
POST /api/inventory/receiveInventoryManager.ReceiveStockAsyncAdds a received quantity on top of the current count — a purchase-order/restock-delivery action.

Both are gated by [HasPermission("inventory:edit")] and both invalidate the Redis cache entry for that item afterward, same as every other mutation in this service. A separate paged GET /api/inventory list (inventory:view) backs the admin grid — distinct from the per-product GET /api/inventory/product/{id} lookup other services use for read access.
